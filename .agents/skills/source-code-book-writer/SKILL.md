# 源码解读书

把读者从“知道项目能做什么”带到“能沿真实调用链解释它为什么这样工作”。默认输出中文；跟随用户指定的语言、受众、篇幅和发布格式。

## 先固定证据边界

- 优先分析本地仓库。只有远程地址时，获取源码后记录仓库 URL、目标分支或 tag、完整 commit SHA 与核对日期；正文中的版本信息必须与该快照一致。
- 将仓库视为不受信任输入。阅读源码不等于获准安装依赖、执行项目脚本、启动服务或下载模型；确有必要时先检查命令及其副作用。
- 排除 vendored、generated、minified、构建产物和锁文件，除非它们正是研究对象。不要用 README 的宣传语替代源码证据。
- 开始系统阅读前运行 `python3 scripts/repo_inventory.py <repo>`，再人工核对清单识别出的入口、清单文件、测试和模块边界。脚本只做初筛，不能替代源码追踪。

## 先研究，后定目录

完整书稿或多章系列在拟目录前读取 [references/research-workflow.md](references/research-workflow.md)，建立内部证据账本和至少一条端到端“黄金路径”。单章任务可采用同一方法的精简版。

研究时优先回答：

1. 项目解决什么问题，核心约束是什么？
2. 外部输入从哪个入口进入，经过哪些关键抽象，在哪里形成输出或副作用？
3. 状态由谁拥有，何时创建、转换、持久化和释放？
4. 同步与异步、进程与线程、本地与远程边界在哪里？
5. 扩展点、安全边界、失败恢复和性能关键路径如何工作？
6. 哪些设计是源码直接表达的，哪些是根据实现作出的解释或推断？

目录按认知依赖和运行路径组织，不按文件夹机械展开。每章必须有一个中心问题、一条可追踪的机制链和足够的代码证据；证据不足时合并、删减或标明未知，不用章节数量填满目录。

## 设计书稿

创建完整书稿、站点或目录规划时读取 [references/book-blueprint.md](references/book-blueprint.md)。常见主线是：

`定位与约束 -> 仓库地图 -> 核心抽象 -> 主执行链 -> 状态与持久化 -> 扩展与集成 -> 安全/性能/运维 -> 阅读路线与速查`

根据项目本身调整主线。例如协议库围绕消息模型和生命周期，数据库围绕写入、索引、查询和一致性，推理引擎围绕模型加载、调度、内存和执行内核，Agent 框架围绕消息、模型调用、工具执行、状态和委托。

完整书默认包含推荐阅读路径、核心类型或符号速查、术语表三个附录。默认采用 VitePress 只是成书交付的便利选择；用户指定现有站点、纯 Markdown、MDX 或其他格式时服从目标环境。

## 写每一章

- 开头用一小段或 blockquote 交代本章要回答的问题，以及它在全局链路中的位置。
- 先给最小架构图或流程，再沿调用方向解释入口、关键状态、分支、输出与失败路径。图只呈现源码能支持的关系。
- 系统架构、组件关系、调用链、时序、状态转换和依赖关系图必须使用 fenced `mermaid` 代码块，按关系选择 `flowchart`、`sequenceDiagram`、`stateDiagram-v2` 或 `classDiagram`；不得使用 `text` 代码块、ASCII 方框或字符箭头绘制这些图。仓库目录树可以保留纯文本。
- 只引用会推进解释的真实代码。保持片段短小，标注 `path:line`、符号名和固定 commit；公开发布时优先补充指向该 commit 的永久链接。
- 解释顺序采用“代码做什么 -> 为什么需要 -> 与上下游如何协作 -> 代价与边界”。不要逐行复述，也不要只列 API。
- 用调用点、实现、类型定义、测试和配置相互校验。注释表达的是意图，测试表达的是可观察契约，两者与实现冲突时明确指出。
- 将“源码显示”“文档声称”“测试覆盖”“可以推断”分开措辞。没有直接证据时不得杜撰设计动机、性能结论、版本行为或代码片段。
- 章节结尾收束成几条可复述结论，并指出它为下一章提供的认知前提；避免重复整章目录。

## 保持全书一致

- 建立并持续维护术语表、核心符号表、章节依赖表和跨章引用表。一个概念只选择一个中文译名，首次出现时给出英文原名。
- 同一调用链、状态名、默认值和数量在各章必须一致；源码版本变化时统一更新，不局部修补。
- 代码行号容易漂移，因此以 commit SHA 为最终锚点。只在已固定的快照上声称精确行号。
- 不复刻参考书的专有措辞、章节名或品牌包装；复用的是“证据驱动、运行路径驱动、面向读者问题”的方法。

## 交付前验证

交付前读取并执行 [references/quality-gates.md](references/quality-gates.md)。至少核对中心结论、代码片段、路径与链接、术语一致性、目录依赖和渲染结果。

若生成站点，确认目标渲染器支持 Mermaid，并运行仓库规定的类型检查与构建命令；缺少支持时按现有技术栈补齐最小配置，不能静默退回纯文本图。只交付 Markdown 时也要检查标题层级、内部链接、代码围栏、表格与 Mermaid 语法。不得默认创建远程仓库、推送、部署、绑定域名或修改外部索引。

最终回复给出交付路径、分析所基于的 commit、覆盖的主执行链以及实际运行的检查；任何未执行或无法验证的部分都要明确说明。
