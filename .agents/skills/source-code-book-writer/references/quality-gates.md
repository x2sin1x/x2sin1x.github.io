# 交付质量门槛

## 证据

- [ ] 记录仓库 URL、本地来源、完整 commit SHA、版本或 tag、核对日期。
- [ ] 每个中心结论都能回到实现、类型、配置、测试或历史证据。
- [ ] 每个代码片段与固定快照逐字一致，省略未改变原意。
- [ ] 路径、符号、默认值、数量和行号已重新核对。
- [ ] 对抽象至少找到一个实现；对实现至少找到一个真实调用点。
- [ ] 文档声明与源码行为不一致时已说明差异。
- [ ] 事实、解释、推断和未知使用了不同措辞。

## 机制与叙事

- [ ] 全书至少完整追踪一条从输入到输出或副作用的黄金路径。
- [ ] 每章回答一个明确问题，并推进全书主线。
- [ ] 章节顺序满足认知依赖，没有先使用后定义的核心概念。
- [ ] 解释覆盖状态所有权、关键分支、生命周期和失败路径，而非只讲理想流程。
- [ ] 设计取舍同时写出收益和代价，没有把实现选择包装成唯一正确答案。
- [ ] 概览、目录、章节和结论对项目能力的表述一致。

## 文字与视觉

- [ ] 首次出现的缩写和关键术语已解释，中文译名全书一致。
- [ ] 段落先给判断，再给代码或机制证据；没有大段逐行复述。
- [ ] 图中的节点、箭头、顺序和数量能由源码支持。
- [ ] 系统架构、组件关系、调用链、时序、状态和依赖图均使用 Mermaid，没有以纯文本或 ASCII 图替代。
- [ ] 每个 Mermaid 代码块语法有效，并已在目标 Markdown 或站点渲染器中实际检查。
- [ ] 表格列数适中，代码围栏语言正确，长行不会破坏渲染。
- [ ] 内部链接、图片路径、锚点和跨章引用有效。
- [ ] 推荐阅读路径体现不同角色的真实目标，而非复制目录。

## 站点与文件

- [ ] 遵循目标仓库的包管理器、目录、格式和构建约定。
- [ ] 未提交缓存、构建产物、依赖目录或分析时的临时文件。
- [ ] 类型检查和生产构建成功；若目标项目没有对应命令，说明采用的替代检查。
- [ ] 在桌面和移动宽度检查导航、表格、代码块、图和长标题。
- [ ] 没有未经请求创建远程仓库、推送、部署、域名、通知或其他外部副作用。

## 抽查方法

交付前随机抽取至少三章，每章反向验证：

1. 从摘要任选一个结论；
2. 找到正文中的机制解释；
3. 找到对应代码引用和固定 commit；
4. 打开源码确认符号、上下文和行号；
5. 找到调用点或测试确认它不是孤立定义。

任何一环断裂，都应修正文稿或降低结论强度，而不是补写未经验证的连接。
