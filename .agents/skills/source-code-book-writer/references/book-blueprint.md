# 成书蓝图

## 规模与结构

章节数由认知负担决定，不由代码行数单独决定：

| 项目复杂度 | 正文章节参考 | 适用情况 |
|---|---:|---|
| 聚焦型 | 8–12 | 单一库、单一主链、抽象较少 |
| 中型 | 13–20 | 多个核心抽象或一个完整运行时 |
| 大型 | 20–26 | 多包、多执行面、持久化与扩展体系齐全 |

超过 26 章时优先按卷或子系统拆分。少于参考数量完全可以；不要为满足模板制造空章。

常用认知顺序：

1. &#8203;**宏观认知**&#8203;：定位、边界、快速运行模型、仓库结构；
2. &#8203;**核心抽象**&#8203;：决定系统语言的类型、接口、状态与注册机制；
3. &#8203;**主执行链**&#8203;：从真实入口到结果，按调用顺序拆章；
4. &#8203;**状态与资源**&#8203;：持久化、缓存、内存、生命周期和恢复；
5. &#8203;**高级机制**&#8203;：并发、调度、扩展点、安全与性能；
6. &#8203;**生态边界**&#8203;：API、CLI、协议、插件、部署和可观测性；
7. &#8203;**附录**&#8203;：角色化阅读路线、核心符号速查、术语表。

不是每个项目都需要每一部分。将篇幅集中在形成项目辨识度的两到四个机制上。

## 不同项目的主线

### Agent 与工作流框架

消息/任务模型 -> Agent 或图抽象 -> 模型调用 -> 工具执行 -> 状态/checkpoint -> 流式输出 -> 记忆/委托 -> 扩展与安全。

### 数据库、检索与记忆系统

数据模型 -> 写入路径 -> 存储布局 -> 索引构建 -> 查询计划 -> 检索/过滤/合并 -> 分片与一致性 -> 恢复和运维。

### 推理与训练系统

模型/权重加载 -> 张量或图抽象 -> 内存/KV 管理 -> 调度与批处理 -> 执行内核 -> 并行与通信 -> 采样/输出 -> 量化与性能。

### 协议与 SDK

参与方与分层 -> 数据模型 -> 传输 -> 生命周期 -> 能力协商 -> 请求/通知 -> 流式与取消 -> 错误、安全和扩展。

### 沙箱与基础设施

控制面 -> 资源创建 -> 隔离边界 -> 文件/网络/凭据策略 -> 执行 -> 资源回收 -> 观测与故障恢复 -> 部署。

这些是选题检查表，不是固定目录。章节标题应反映该项目的具体机制，而不是通用分类名。

## 默认 VitePress 交付

用户要求完整电子书但未指定载体时，可使用轻量 VitePress 结构：

```text
book/
├── .vitepress/
│   └── config.ts
├── chapters/
│   ├── 01-overview.md
│   ├── 02-repo-structure.md
│   ├── ...
│   ├── appendix-a-reading-path.md
│   ├── appendix-b-symbol-reference.md
│   └── appendix-c-glossary.md
├── public/
├── index.md
├── contents.md
└── package.json
```

如果目标仓库已有文档站，优先融入现有目录、包管理器、主题和链接约定，不平行搭建第二套站点。不要默认增加域名、部署工作流、遥测、远程通知或发布步骤。

首页只承诺正文真正覆盖的内容：一句定位、一句读者收益、开始阅读与目录入口、两到四个最有辨识度的机制。目录页按部分分组，并让章节依赖关系可见。

## 章节构造

每章应完成一段推理，而不只是覆盖一个模块。可按需要组合：

1. &#8203;**问题与位置**&#8203;：本章解释什么，它连接哪两个环节；
2. &#8203;**源码坐标**&#8203;：入口文件、核心符号和相关测试；
3. &#8203;**最小模型**&#8203;：组件图、状态图、时序图或关键数据结构；
4. &#8203;**执行追踪**&#8203;：沿一次真实输入逐跳解释；
5. &#8203;**机制深挖**&#8203;：关键分支、状态变化、生命周期或算法；
6. &#8203;**设计取舍**&#8203;：为何这套组合合理，代价和替代方案是什么；
7. &#8203;**失败边界**&#8203;：错误、取消、回滚、资源耗尽或不支持场景；
8. &#8203;**本章收束**&#8203;：三到五条结论，以及下一章的前提。

不必让所有章节使用相同标题。概览章重在心智模型，仓库结构章重在依赖方向，核心机制章重在调用链，部署章重在运行边界。

## 代码、图与表

- 代码片段通常保留 5–30 行，只展示解释所需的签名、状态变化和关键分支。
- 系统架构图、组件关系图、调用链图、时序图、状态图和依赖图一律使用 fenced `mermaid` 代码块，不使用 `text` 代码块、ASCII 方框或字符箭头模拟图形。
- 静态边界优先用 `flowchart` 或 `classDiagram`，交互顺序用 `sequenceDiagram`，状态转换用 `stateDiagram-v2`；一张图只承担一种解释任务。
- Mermaid 节点 ID 保持简短稳定，展示文本与 ID 分离；包含空格、标点或代码符号的标签使用引号，避免依赖渲染器的宽松解析。
- 目录树只保留影响理解的路径，并在每个路径后写职责，避免粘贴整个仓库。
- 表格适合接口对比、实现差异、配置矩阵和角色化阅读路线；单列长文不应强行做表。
- 性能数字必须来自可复现 benchmark 或项目报告，并携带版本、硬件、数据集和参数语境。

## 三个附录

- &#8203;**推荐阅读路径**&#8203;：按快速理解、核心贡献、扩展开发、生产运维等读者目标组织，不只是重复目录。
- &#8203;**核心符号速查**&#8203;：给出符号、职责、定义位置、主要调用者和所属章节。
- &#8203;**术语表**&#8203;：统一项目术语、缩写和中文译名，不收录正文从未使用的百科条目。
