# 论文博客化解读

把论文写成一篇读者愿意从头读完的技术博客，而不是压缩版论文。文章先让读者看见问题和旧方案的失败点，再给出能改变这一局面的洞察，最后用少量机制与证据完成闭环。

默认输出中文 Markdown；跟随用户指定的语言、发布平台和受众。保留方法名、模型名、数据集、指标及其他有辨识度的英文术语。

## 取证

- 先确认论文标题、作者、版本、发表状态，以及官方项目页、代码和模型链接。arXiv 未指定版本时使用当前最新版，并记录版本号和核对日期。
- 至少核对摘要、引言、方法、主实验、关键消融、结论与相关附录。项目状态、安装命令和 API 以当前官方仓库或文档为准，不能用论文中的旧状态替代。
- 在写作前建立内部证据表：`主张 | 原文位置 | 适用条件 | 事实/解释/推断 | 可否进入正文`。最终文章不必展示这张表。
- 给每个数字带上最小必要语境，包括模型、任务或数据集、解码设置、硬件/后端、baseline 与统计口径。`最高`、`平均`、`端到端`、`lossless` 等词不得互换。
- 论文、官方代码与项目页不一致时说明时间或版本差异。无法确认的内容写明未知，不补造命令、配置、图表或因果关系。
- 可以借鉴用户给出的页面节奏和信息组织，但不要复刻其独特措辞。将示例中的具体机制抽象为叙事功能，不要把 DFlash 的章节或术语强加给其他论文。

## 建立故事主线

写正文前，各用一句话回答：

1. 任务为什么重要，真正卡在哪里？
2. 当前最强或最直观的方案怎样工作，为什么仍受限？
3. 看似自然的替代方案为什么也不够？
4. 论文提出了哪个可复述的关键问题？
5. 哪个核心洞察改变了原来的权衡？
6. 哪两到四个机制把洞察变成系统或方法？
7. 哪项实验最直接证明主张，证据边界在哪里？
8. 这项工作改变了读者看待什么问题的方式？

如果无法形成“旧方案受限 -> 朴素替代失败 -> 关键问题 -> 洞察 -> 机制 -> 证据”的因果链，继续读原文，不要先写章节。

## 组织文章

需要完整博客或项目页时，读取 [references/blog-template.md](references/blog-template.md)。用户明确提到 DFlash、Z Lab 风格，或需要校准成稿节奏时，再读取 [examples/DFlash.md](examples/DFlash.md)。

文章通常采用以下阅读顺序，但可按论文特点删减或改名：

- 标题、作者/发表信息与 Paper / Code / Models 等高价值入口。
- 两段式开场：第一段建立瓶颈，第二段说方法做了什么并给出一个有范围的代表结果。
- 可选 Quick Start：仅在存在官方可运行实现且对目标读者有价值时放在前部。
- `Why [方法名]?`：先解释 baseline，再展示朴素替代为何失败，最后用一个具体问题完成转折。
- `How [方法名] Works`：先讲关键洞察与它为何改变原有权衡，再用总览图和两到四个机制落地。
- `Results`：交代公平比较所需的设置，只呈现最能验证主张的一张图或一张表，再补充泛化、部署结果或边界。
- `Conclusion`：先收束本文证明了什么，再写它带来的研究视角变化。资源和引用按发布场景选配。

不要机械输出 `Abstract`、`Related Work`、`Contributions`、`Limitations` 等论文目录。必要的限制应贴着对应结果写，不能藏在文末免责声明里。

## 写作节奏

- 每段承担一个推进动作，通常为两到四句。先给判断，再解释原因或证据。
- 首次出现概念时用一句白话说明其角色，随后再使用术语；不单独堆砌术语表。
- 用对比讲机制：旧方法做什么、因此受什么限制；新方法改了哪一步、所以哪个量发生变化。
- 全文只在关键转折处使用一到两个设问。设问必须由前文推出，并由后文立即回答。
- 允许短促的总结句作为记忆点，但它必须压缩已经解释过的因果关系，不能代替论证。
- 语气可以鲜明，范围必须克制。将“论文报告”“实验显示”“这意味着”和“可以推断”区分开。
- 中立解读默认称“论文”或方法名；只有用户明确要求作者/实验室项目页口吻时才使用“我们”。
- 公式只在它揭示关键权衡时保留，并先解释变量与直觉。实现细节只保留会改变读者理解或复现路径的部分。

## Quick Start

- 只采用官方仓库或官方文档当前提供的安装与使用方式，注明核对日期或版本。论文已有代码但接口仍在开发时，直接说明，不拼凑命令。
- 优先给一条最短的探索路径和一条生产/集成路径；避免把 README 全部搬入博客。
- 不执行需要下载大模型、占用昂贵 GPU、写入外部系统或携带凭据的命令，除非用户明确要求且环境合适。未运行的命令标为“依据官方文档核对”，不能声称已实测。

## 图表与证据

- 优先使用一张方法总览图和一张主结果图。只有当额外图表承担新的论证功能时才增加。
- 图片紧跟首次深入解释它的段落。alt text 说明对象、变量与关键关系；图注说明它支持什么结论，而不是重复图名。
- 可将论文表格重绘为更易读的表或图，但数值必须逐项核对，并标注为“根据原论文 Table/Figure N 重绘”。不能从像素估读精确值。
- 结果段先写比较条件，再写趋势和代表数字，最后写不能推出什么。图表不能替代文字推理。
- 使用本地图片时将其放入交付文件旁的 `assets/` 并检查相对路径；使用远程图片时采用稳定的官方来源，并保留来源链接。

## 交付检查

- 默认交付一个可独立阅读的 Markdown 文件；用户指定 Hugo、VitePress、MDX 或项目站点时再适配 front matter 与组件语法。
- 检查开场的结果是否能在实验段找到证据，方法机制是否各自回应了前文瓶颈，结论是否超出实验范围。
- 检查标题层级、链接、图片、代码块和表格渲染。删除空章节、占位文本与不再引用的资源。
- 回复中给出文件链接，并用一句话概括文章的“瓶颈 -> 洞察 -> 证据”主线。
